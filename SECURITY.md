# Security Policy

## Scope

Security issues in this project may include conventional software vulnerabilities as well as privacy-specific failures such as accidental raw-text logging, exposure of secrets, unsafe pseudonymization, or benchmark artifacts containing real personal information.

## Do not publish sensitive reports publicly

If a security report requires sharing:

- working credentials,
- private dataset samples,
- unredacted personal data,
- exploit details that would create immediate risk,

use **[GitHub private vulnerability reporting](https://github.com/soulipaco/pii-reduction/security/advisories/new)** rather than a public issue. It is enabled on this repository, so the *Report a vulnerability* button under **Security** opens a draft advisory visible only to you and the maintainer.

This was enabled at the moment the repository became public (2026-08-22). Until then the paragraph above forbade the public tracker without offering anywhere else to go, which is a worse failure than no policy at all.

## Examples of security/privacy issues

- Databricks token committed to history.
- Raw PII written to ordinary application logs.
- Exception messages containing complete source transcripts.
- Audit table storing raw entity values contrary to configuration.
- External model/API receiving source text despite being configured as local-only.
- Deterministic pseudonymization implemented with an unkeyed predictable hash.
- Reversible mapping table exposed to users of reduced outputs.
- Path traversal or arbitrary file access through source configuration.
- Unsafe deserialization of configuration/model artifacts.
- SQL injection through dynamically constructed table identifiers.
- Public demo dataset unexpectedly containing real PII.

## Secret handling

No real secret should appear in:

- source code,
- notebooks,
- Markdown,
- test fixtures,
- screenshots,
- CI logs,
- example configuration.

If a secret is committed, removing it from the latest commit is insufficient. Rotate/revoke it and clean repository history where appropriate.

## PII handling

The repository's committed test data must be synthetic or explicitly public-safe.

Reduced text should still be treated cautiously because automated detection can miss entities.

## Dependency security

Pin or constrain important dependencies appropriately and keep provider/model dependencies isolated where possible.

Before public releases, review:

- Python dependency vulnerabilities,
- model licenses,
- dataset licenses,
- transitive packages introduced by NLP frameworks.

## Databricks integration

Databricks examples should use configurable object names and supported authentication mechanisms.

Avoid dynamically concatenating unvalidated user input into SQL object references. Where object identifiers must be configurable, validate allowed catalog/schema/table identifier patterns.

## Pseudonymization

The default public release should favor irreversible redaction.

If deterministic pseudonymization is enabled:

- use a keyed construction,
- keep the key outside Git,
- document scope and collision behavior,
- do not imply that pseudonymization equals anonymization.

## External providers

Any provider that sends text outside the executing environment must be marked clearly as external and disabled by default unless the user intentionally configures it.

Provider documentation should state:

- execution boundary,
- authentication requirement,
- whether source text leaves Databricks/local runtime,
- audit/cost implications.

## Release checklist

Before publishing a release:

- scan Git history for credentials,
- confirm demo assets are public-safe,
- inspect logs generated by the demo,
- verify `.env` and private datasets are excluded,
- review new dependencies/licenses,
- run privacy regression tests,
- ensure README does not make unsupported compliance claims.
